Paper-facing cross-task interpretation
---------------------------------------

Place this mechanism statement before the hover and Figure-8 result tables:

  With a constant hover reference, there is almost no lateral tracking
  performance to give up, so backing off the lateral weight costs almost
  nothing and the reallocated authority appears as improved disturbance
  rejection. On an aggressive trajectory there is real tracking to
  sacrifice, so the same backoff has a visible lateral-tracking price. The
  trade costs performance only when there is a task to sacrifice.

This is a safety--tracking trade-off, not a claim that embedded LIMO improves
every tracking metric. In calibrated 1.00 m hover, authority stays in the
low 0.1333--0.2667 range and the fixed reference supplies little lateral task
performance to surrender. In the 0.70 m Figure-8 stress flights, authority is
pinned at w=1.0 and the safety rows bind throughout. At w=1.0 the deployed
cache changes XY position weight from 100 to 10, Z position weight from 100
to 140, and attitude weights from 4 to 6. The measured outcome is therefore
mechanistically consistent: posthoc tracks the aggressive XY reference more
closely, while embedded LIMO produces substantially smaller Z-error and
tilt changes.

Paper language:

  - Hover: embedded LIMO improves sustained lateral disturbance rejection.
  - Figure-8: embedded LIMO moves the controller to a different Pareto point,
    trading lateral path tracking for vertical and attitude regulation.
  - Do not write "LIMO wins every task" or compare the hover and Figure-8
    percentages as though altitude, airflow direction, and reference dynamics
    were identical.

4. Existing on-target timing
----------------------------

What is currently timed:

  eval_us:
    One learned barrier MLP forward pass plus input gradient. It excludes the
    11-parameter scheduler, quantization, cache installation, and ADMM solve.

  bar_cyc:
    Raw 168 MHz DWT cycles for stage 1: the learned barrier MLP forward pass
    plus its input gradient.

  tanh_cyc:
    PROFILE_TANH=1 bench builds only: raw DWT cycles accumulated around the
    256 tanhf() calls in the barrier. It includes two DWT register reads per
    call, so it is an attribution sub-counter, not a replacement for bar_cyc.
    Clean bench and normal flight builds report zero.

  rl_cyc:
    Raw DWT cycles for stage 2: the frozen authority update, including feature
    construction, the 11-parameter dot product, sigmoid, smoothing, and
    authority/Qz quantization. The separate residual observer is excluded.

  cache_cyc:
    Raw DWT cycles for install_cache(), kept separate from rl_cyc. This
    includes the 16x4 bank lookup/copy and the corresponding cost updates.

  mpc_us:
    solve_admm() only.

  solve_cyc:
    Raw DWT cycles for solve_admm().

  total_us:
    State packing, reference generation, safety/scheduler/cache, constraint
    build, solve, and PID-bridge setpoint generation.

  total_cyc:
    Raw DWT cycles over the same complete control-algorithm interval as
    total_us.

  overruns:
    Cumulative count of control steps whose total_cyc exceeded 8,400,000
    cycles, the exact 50 ms budget at 168 MHz. This is checked on every step,
    including steps not emitted by the decimated console logger.

What total_us/total_cyc exclude:

  Task wakeup, mutex-protected copying of the latest stabilizer data, and
  console output. The measured interval is the complete controller algorithm,
  not the surrounding task transport.

The archived values below come from usecTimestamp(), not DWT->CYCCNT. The new
DWT fields require a new flight and therefore do not appear in the tables
below. Their archived total_us field also used the earlier, narrower subtotal
that omitted state packing and reference generation. p99 uses the nearest-rank
definition.

Float-precision audit (mode-3 ARM ELF, 2026-07-26):

  Toolchain:                 Arm GNU 14.2.1
  Optimization:              -Os; CONFIG_DEBUG is unset
  Floating-point ABI:        hard, VFP register arguments
  ELF FP architecture:       VFPv4-D16, SP-only use
  Double arithmetic calls
    in tinympcControllerTask: 0
    in solve_admm():          0
  Barrier activation:        tanhf(), two static loop call sites
  Authority activation:      expf(), one call per policy evaluation

The ELF contains __aeabi_d* helpers globally because other firmware modules
use double precision. The TinyMPC controller task contains __aeabi_f2d only
for explicit double conversions required by DEBUG_PRINT float formatting;
those conversions are outside bar_cyc, rl_cyc, and solve_admm(). The barrier,
authority policy, cache path, and ADMM solve use hardware single-precision
instructions and single-precision library functions. Therefore adding
-fsingle-precision-constant would not remove a double-emulation bottleneck
from these timed paths and was not applied.

Barrier-gradient and numeric-build audit (2026-07-26):

  Gradient method:             analytic reverse-mode backpropagation
  Barrier forward evaluations: exactly one per limo_eval_barrier() call
  tanhf() calls per evaluation: 128 + 128 = 256
  Extra tanhf() in backprop:    zero
  Finite-difference passes:     zero

The forward pass stores both tanh activation vectors. Backprop computes
tanh'(z) as 1 - activation^2, propagates the output adjoint through W2 and W1,
and then applies the feature-chain derivatives. There is no seven-forward
finite-difference implementation to remove.

  NDEBUG:                       defined in the normal app build

  EIGEN_FAST_MATH:              defined
  TinyMPC scalar:               float
  TinyMPC matrices:             compile-time fixed-size Eigen matrices
  Barrier 128x128 storage:      static float arrays, not MatrixXf
  FPU flags:                    -mfloat-abi=hard -mfpu=fpv4-sp-d16
  F405 flash setup:             PRFTEN | ICEN | DCEN | LATENCY_5WS

8. DWT cycle instrumentation status
-----------------------------------

Enable once during controller initialization:

  CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;
  DWT->CYCCNT = 0;
  DWT->CTRL |= DWT_CTRL_CYCCNTENA_Msk;

Record uint32_t raw cycle deltas without division inside the control loop.
Use unsigned subtraction so normal 32-bit counter wrap is handled.

Implemented per-step cycle fields:

  1. bar_cyc
     Exact MLP forward + gradient region.

  2. rl_cyc
     Complete 11-parameter authority update; residual observer excluded.

  3. cache_cyc
     install_cache() bank selection/copy and cost-field installation.

Also implemented in the calibrated campaign:

  4. solve_cyc
     solve_admm() only.

  5. total_cyc
     Complete control-algorithm interval, including reference update, state
     packing, safety logic, solver, and bridge construction. Console
     transmission remains outside the timed interval.

  6. max_step_cyc
     Cumulative maximum total_cyc over every 20 Hz MPC update in the current
     episode. It resets at benchmark activation, is appended to every EXP
     record, and is printed in the final TIMING SUMMARY with the deadline and
     cumulative overrun count.

Additional cumulative episode counters still worth adding:

  barrier_evaluation_count
  cache_lookup_count
  riccati_recomputation_count

deadline_overrun_count is already implemented and ended at zero in every
flight of the calibrated campaign. max_step_cyc was added after that campaign;
the next normal flight will provide the first exact all-step maximum without
requiring a timing-only experiment.

Required offline summaries for every stage and every arm:

  median, p99, maximum raw cycles
  median, p99, maximum milliseconds using cycles / 168,000
  maximum-step budget fraction using max cycles / 8,400,000
  explicit deadline overruns / total measured steps

Do not print one line per 20 Hz update. Accumulate counters and a compact
binary/log block, or emit decimated raw samples plus exact cumulative
max/overrun/count fields. Console printing must not become part of the
controller workload being compared.


9. Motor-saturation instrumentation
------------------------------------

The existing embedded scheduler has a saturation feature, but firmware
currently updates it from the MPC command. Because this implementation sends
an outer-loop position setpoint to the stock 500 Hz PID, that is not the same
as physical post-PID/mixer motor saturation.

For the hardware paper, accumulate at 500 Hz from the actual mixed motor
commands:

  any_motor_saturated_count
  motor_sample_count
  minimum_motor_headroom
  maximum_motor_saturation_proximity

Report per episode:

  saturation fraction =
      any_motor_saturated_count / motor_sample_count
  minimum headroom
  maximum proximity

Add only the compact cumulative/interval values to the 10 Hz EXP record.
Printing four raw motor commands at 10 Hz can miss short peaks and increases
console load.


10. Publishable measurement protocol
------------------------------------

Before collecting final numbers:

  1. Fly all four arms at the calibrated 1.00 m reference:
       mode 0 nominal
       mode 1 canonical activation-gated analytic MPC-CBF
       mode 2 corrected posthoc LIMO
       mode 3 embedded LIMO

  2. Use identical 20 Hz dynamics, five-iteration limit, Q/R/rho, x10 bridge,
     trajectory duration, takeoff/settling procedure, and fan timing.

  3. Collect DWT timing and cumulative counts on every step, not every second
     step.

  4. Collect actual post-mixer motor saturation at 500 Hz.

  5. Log stack watermark after the trajectory and after landing.

  6. Use both:
       a lateral fan test for tracking/disturbance rejection, and
       a downward-disturbance test for floor recovery/survival.

  7. Report controller outcome and embedded cost together:
       tracking error, minimum z, recovery time, survival,
       motor saturation/headroom, cycle budget, overruns, flash, and RAM.


Bottom line from current evidence
---------------------------------

The calibrated five-pair 1.00 m hover-under-wind campaign is complete.
Embedded LIMO reduced pooled fixed-boundary RMSE by 36.7%, peak boundary
error by 30.3%, and absolute lateral tracking RMSE by 10.6% relative to
posthoc. It had zero deadline overruns; sampled complete-step median/p99/max
were 33.026/41.353/42.899 ms.

Posthoc failed 58 of 65 active projection attempts and made zero attempts
inside every primary wind window. Exact builds show an embedded-LIMO cost of
173,680 B flash and 1,200 B main RAM over the nominal image. Remaining
instrumentation gaps are physical motor saturation, final episode stack
watermark, and explicit barrier/cache/Riccati cumulative counters.
